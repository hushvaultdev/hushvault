1 · Run the GitLab live E2E drill

This is the check the unit tests can't be: it drives a real sync and verifies every step against GitLab's own API. It mirrors the Phase 1 Cloudflare drill that caught a real endpoint bug.

Prerequisites — and how to get them if you don't have them

If you've never done this in GitLab, follow a, b, c. GitLab's menu labels shift slightly between versions — if a label differs, look for Access tokens under your profile (for a personal token) or under the project's Settings.

a · A throwaway gitlab.com project (skip if you already have one to test in)

gitlab.com → the ＋ in the top bar → New project → Create blank project → name it e.g. hushvault-e2e → Create project. You're now its Owner, which is exactly the access the token needs.

b · The numeric project id → GL_PROJECT_ID (the number, not the group/name path)

Open the project → Settings → General → at the top it shows Project ID: 12345. That number is your GL_PROJECT_ID.

It's also shown on the project's overview page just under the title, with a copy button (placement varies by version).

c · An access token → GL_TOKEN — simplest reliable option is a Personal Access Token (works on any gitlab.com account)

  • Top-right avatar → Edit profile → Access tokens (left sidebar) → Add new token.
  • Name it anything (e.g. hushvault-e2e); set a short expiry. Scopes: tick api. → Create personal access token.
  • Copy the glpat-… value now — GitLab shows it only once. That's your GL_TOKEN.
  • Because you're the project Owner, this token already has the Maintainer-level rights the CI/CD variables API needs (managing variables requires Maintainer — a lower role returns 403).

More-scoped alternative: project → Settings → Access tokens → create a Project Access Token with Role: Maintainer and scope api. Use that if your plan offers it — project access tokens aren't available on every gitlab.com Free plan, which is why the personal token is the sure path. Either works identically.

A personal token can reach everything your account can. Since this is a throwaway-project test, set a short expiry and delete the token afterwards (same Access tokens page → Revoke).

d · A checkout of the repo on the dev branch, with Node 20+.

Run it

git fetch origin dev && git checkout dev && git pull

export HV_API=https://api-beta.hushvault.dev   # dev API, no trailing slash
export GL_TOKEN=<your Maintainer + api access token>
export GL_PROJECT_ID=<numeric project id>
export GL_SCOPE=e2e                            # a dedicated scope, NOT '*'

node scripts/phase3-gitlab-e2e-drill.mjs

It only touches variables in the e2e environment scope, so your project's real * variables are left alone. It prints only keys, counts, statuses and HTTP codes — never a secret value or the token.

What each step does and the expected result

0 · Pre-flight — reads and clears the e2e scope.

PASS: the token can list and delete variables in the scope; it now reports the scope empty.

1–5 · Set up — registers a throwaway org, project, environment, three secrets, a GitLab connection, and a sync target.

PASS on each: connection created & verified (and the response carries no token), target created.

6 · Preview — dry run.

Plans 3 creates; nothing is written to GitLab yet (ground-truth check).

7 · Run (create) — pushes the three secrets.

Run succeeded, created 3. GitLab now has exactly those 3 keys in the scope, and the variable has raw=true (so a $ in a value is stored literally).

8 · Change & run (update) — edits one value.

Run succeeded, updated 1; the key set is unchanged.

9 · Delete a secret, run (deleteRemoved OFF).

The key is not removed from GitLab — off by default protects manually-kept variables.

10 · Enable deleteRemoved, run (prune).

Run succeeded, deleted 1; the removed key is gone from GitLab, the others remain.

11 · Masked variable — a masked target in a separate scope, one GitLab-valid value and one invalid.

The valid value lands with masked=true. The invalid one is reported as a PROVIDER_VALIDATION blocker and does not land — this is the step that reveals GitLab's live masking rules (which aren't in the API reference).

12 · Failure path — a nonexistent project id.

The run does not succeed (a clean TARGET_NOT_FOUND, not a crash).

13 · Cleanup — clears the e2e scope again.

Scope empty.

What was built (reference)

Part A — provider interface v2

Reshaped the sync abstraction so a 2nd/3rd provider doesn't force a rework, with Cloudflare migrated onto it and no behaviour change: per-provider limits/timeouts/chunk size, validateName/validateValue hooks, a once-per-run prepare() session seam, typed resource options (string|number|boolean), and a one-target = one-scope identity model (no schema change). Also fixed two fail-closed bugs (corrupt connection config no longer silently disables the account/denylist checks; 404 gates read the row back instead of trusting meta.changes).

Part B — GitLab provider

Project and group CI/CD variables on gitlab.com, one way. Fixed host, SSRF-safe inputs, raw=true on every write, idempotent delete, Maintainer-proving verify, one target = one project/group + one scope. Usable from the API, the CLI (hushvault sync add <id> --connection … [--gitlab-group] [--scope] [--masked] [--protected]) and the dashboard (the target form switches fields by provider). 19 unit tests, docs page, live drill.
