HushVault

Set up secret sync — and check it works

Connect HushVault to the places your app reads its secrets — Cloudflare Workers, GitHub and GitLab — so that when you change a secret in HushVault, it flows out to all of them automatically. This guide walks you through setup and then a short set of checks to prove it's working.

Sync is one-way: HushVault writes to your destinations and never reads your secrets back. Cloudflare Workers and GitLab are in beta; GitHub is in validation — running the checks below is exactly how it gets confirmed. You need an admin HushVault account.

1 Get your access tokens ready

Create one token per destination you want to sync to, with the smallest permission that works. You paste each into HushVault once; it is encrypted and never shown again.

DestinationCreate a…Give it exactlyYou'll also need
Cloudflare WorkersAccount API tokenWorkers Scripts → Edit, for the one accountYour 32-character account ID
GitHubFine-grained personal access tokenRepository → Secrets → Read and write, for the repo(s)The owner/repo of each repository
GitLabProject (or group) access tokenMaintainer role + api scopeThe project's numeric ID (Settings → General). gitlab.com only

Set a short expiry on each token while you're trying this out, and delete it afterwards if you no longer need it. Never sync your master key or JWT secret — HushVault refuses those by design.

2 Connect each destination

In HushVault, open Integrations and choose Connect. Pick the provider, paste the token, and fill in the one detail it asks for (Cloudflare account ID; nothing extra for GitHub or GitLab). HushVault checks the token with a read-only call before saving it.

✓ You should see: the new connection listed, with no token shown — just a label and "last verified" time.

3 Map a secret set to a destination

Still in Integrations, choose Add target. Pick the project and environment whose secrets you want to push, choose the connection, and enter the destination:

  • Cloudflare: the Worker name
  • GitHub: the owner and repository
  • GitLab: the project (or group) ID, and optionally an environment scope / masked / protected

Then click Preview — this shows exactly what would happen, by name, and writes nothing.

What preview tells you

Create = new secrets that will be added · Update = changed values · Skip = already up to date or reserved · Conflict = a name already in the destination that HushVault didn't create (left untouched) · Blockers = names the destination can't accept, each with a suggested rename.

4 Run the first sync

Click Run. HushVault pushes the environment's secrets to the destination.

✓ You should see: the run finishes succeeded, with a count of how many were created. Now open the destination and confirm the names are there:
  • Cloudflare: your Worker → Settings → Variables and Secrets.
  • GitHub: the repo → Settings → Secrets and variables → Actions.
  • GitLab: the project → Settings → CI/CD → Variables.

You'll see the secret names in each destination, never the values — that's how these platforms (and HushVault) protect them.

5 Check it stays in sync when you change a secret

This is the heart of it. Turn on Sync on change for the target (in the target's settings). Then, in HushVault, change one secret's value and save.

✓ You should see: within about a minute, the destination shows the secret as recently updated — no manual run needed. Repeat for a destination of each type to confirm the change lands on Cloudflare, GitHub and GitLab.

6 Confirm the safety behaviours

These are the guarantees worth seeing with your own eyes.

A name the destination can't accept is caught, not mangled

Add a secret named like db-url (a dash isn't allowed on GitHub or GitLab) and preview.

You should see

A blocker with a suggested rename (e.g. db-url → DB_URL). Nothing is pushed under a changed name — you rename it yourself. HushVault never silently renames a secret.

Secrets you created by hand are never touched

In the destination, add a variable HushVault didn't create, then run a sync.

You should see

That variable listed as a conflict in the preview and left exactly as-is. HushVault only ever changes the names it created.

Removing a secret doesn't delete it downstream — unless you ask

Delete a synced secret in HushVault and run. By default the name stays in the destination. Turn on Delete removed secrets on the target and run again.

You should see

Only with the toggle on is the name removed downstream — and only because HushVault created it. Off by default protects you from surprise deletions.

7 Check failure and recovery

In the provider, revoke or expire the token you connected, then change a secret (or run the target).

✓ You should see: the target flips to Needs attention and the organisation's owners get an email (no secret values in it — just which target and why). Rotate the credential on the connection, and the target reactivates and catches up on its own, without a manual run.

8 You're done

If every check above behaved as described, sync is working end to end for your destinations. Day to day:

  • Change a secret in HushVault — it propagates automatically to every target that has sync-on-change.
  • Watch the run history on any target to see what happened and when.
  • If a target ever says Needs attention, open its history for the reason (usually a name to rename or a token to rotate); it resumes on its own once fixed.
  • Remove a target to stop syncing it (nothing is deleted downstream). Remove a connection to revoke its token and all its targets.
HushVault secret sync · one-way, write-only to your destinations · your secret values are never displayed or sent anywhere except, encrypted, to the destinations you connect.
